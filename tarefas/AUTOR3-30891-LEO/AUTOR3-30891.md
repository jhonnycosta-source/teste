Description

VISÃO DO USUÁRIO:

Eu como Analista Interno
Quero que a API valide o perfil de acesso, o estado da cotação e os dados de entrada do prêmio informado
Para que apenas solicitações válidas e autorizadas sigam para o fluxo de alteração

ESCOPO - Lista de Funcionalidades

✅  Resumo da tarefa

Implementar endpoint para receber os prêmios informados e realizar as validações correspondentes

🛠️ Implementação Técnica

auto-cotacao-app:

1. Contrato da API (cotacoes.yaml)
   1.1. Rota e Método: Adicionar a especificação do endpoint PUT /ofertas/{numeroCotacao}-{versaoCotacao}-{numeroOrcamento}/premios no arquivo cotacoes.yaml.

1.2. Request Body: O corpo da requisição deve ser um array contendo objetos com as propriedades:

numeroItem (Integer) - Número do item;

codCobertura (Integer) - Código da cobertura;

valorPremio (BigDecimal/Number) - Valor do prêmio informado.

1.3. Response Body: O retorno deve ser o objeto do Orçamento com todos os valores de prêmio e dados atualizados.

2. Camada Business (CotacoesServiceImpl / Regras de Negócio)
   2.1. Feature Toggle:

Incluir no arquivo de properties e enum de toggles a chave AUTO_COTACAO_PREMIO_INFORMADO com valor padrão desligado (false).

Validar se a toggle está ativa. Caso esteja desativada, devolver HTTP 404 Not Found.

2.2. Validação de Perfil de Acesso:

Validar através da classe PerfilUtil se o usuário solicitante possui o perfil de Analista Interno.

Se o usuário não tiver o perfil adequado, lançar a exceção BusinessUncheckedException.

2.3. Validação dos Dados da Requisição:

Validar se o prêmio recebido no payload é null ou se o seu valor é igual a 0.

Caso seja inválido, lançar BusinessUncheckedException indicando valor inválido.

2.4. Busca e Validação do Orçamento:

Buscar o orçamento pelos parâmetros {numeroCotacao}, {versaoCotacao} e {numeroOrcamento} utilizando o método existente buscarOrcamentoValido no repositório.

O método deve desconsiderar/invalidar orçamentos que possuam os status 4 e 19 do StatusOrcamentoEnum.

Se o orçamento não for localizado ou possuir um status inválido, devolver HTTP 404 Not Found.

2.5. Validação do Motivo de Congelamento:

Obter o motivo do congelamento via TipoMotivoCongelamentoEnum.

Validar se o motivo é diferente de 4 (MOTIVO_FLEXIBILIZACAO). Caso seja diferente, lançar BusinessUncheckedException.

3. Retorno
   Se todas as validações passarem com sucesso, retornar HTTP Status ou 204 No Content (Inicialmente deverá retornar 204 pois o endpoint ainda não terá o orçamento como retorno).

Escopo a ser tratado em outra história:

2.6. Atualização dos Valores de Prêmio:

Localizar cada cobertura pela combinação de numeroIte e codCobertura.

Atualizar exclusivamente os valores das colunas:

CTCPRMVLR

AVYOFRPRMVLR

PSGCRTDSCPRMVLR

PSGAVSTCRTDSCPRMVLR

PSGCRTCRZVNDDSCPRMVLR

PSGAVSTCRTCRZVNDDSCPRMVLR

Importante: Os demais campos referentes ao prêmio anual e memória de cálculo devem permanecer intactos.

2.7. Salvamento:

Salvar as alterações do orçamento na base de dados.

2.8. Flag de Prêmio Informado:

Marcar a nova coluna do orçamento no banco de dados com a flag "S" (Prêmio Informado).

2.9. Recálculo das Formas de Pagamento:

Executar o método existente atualizarFormasDePagamento da classe CotacoesServiceImpl.

Premissa: A execução deste método exige que a toggle AUTO_PROPOSTA_FORMA_PAGAMENTO esteja ativa.

2.10. Mappers e Contratos:

Ajustar os mappers e schemas de contrato para devolver no response a flag da nova coluna de prêmio informado.

3. Retorno da API
   Retornar o orçamento com a cotação totalmente atualizada (HTTP Status 200 OK

Neste primeiro momento, deve-se retornar 204 em caso de sucesso, pois o endpoint ainda não terá o orçamento completo para devolver no response

4. Cobertura de Testes
   Criar e ajustar os testes unitários e de integração contemplando todos os fluxos de sucesso, validações e cenários de exceção descritos.

CRITÉRIOS DE ACEITE

CENÁRIO 1 - Feature Toggle Desativada
Dado que a toggle AUTO_COTACAO_PREMIO_INFORMADO está desativada (default),
Quando o endpoint PUT /ofertas/{numeroCotacao}-{versaoCotacao}-{numeroOrcamento}/premios for acionado,
Então a API deve retornar HTTP 404 Not Found.

CENÁRIO 2 - Permissão do Usuário
Dado que a toggle AUTO_COTACAO_PREMIO_INFORMADO está ativa,
Quando a requisição for feita por um usuário que não possui o perfil de Analista Interno (validado via PerfilUtil),
Então a aplicação deve lançar a exceção BusinessUncheckedException.

CENÁRIO 3 - Validação de Prêmio Nulo ou Zero
Dado que os dados de entrada foram enviados no payload,
Quando o campo valorPremio for null ou igual a 0,
Então a aplicação deve lançar a exceção BusinessUncheckedException informando valor inválido.

CENÁRIO 5 - Motivo de Congelamento Divergente
Dado que o orçamento foi encontrado com sucesso,
Quando o motivo de congelamento (TipoMotivoCongelamentoEnum) for diferente de 4 (MOTIVO_FLEXIBILIZACAO),
Então a aplicação deve lançar a exceção BusinessUncheckedException.

CENÁRIO 6 - Validações Aprovadas com Sucesso
Dado que todas as regras das etapas 2.1 a 2.5 foram atendidas com sucesso,
Quando a requisição for processada,
Então a API deve retornar HTTP Status ou 204 No Content confirmando a validação da cotação.
